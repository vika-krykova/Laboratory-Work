# Лабораторная работа 4 — Система сбора веб-данных (Scrapy + Playwright)

Полноценная система сбора данных с веб-сайтов двух типов:
- статические (SSR) — через классический Scrapy
- динамические (SPA) — через Playwright + JS-рендеринг

Проект реализует полный пайплайн из лекции 4: сбор → очистка → валидация → экспорт.

ЗАПУСК
-----------------------------------------------------------

Сбор новостей с Хабра (SSR):

    python run_spider.py --spider news --days 365 --output news.json

Собирает новостные статьи за последние 365 дней. Обходит 6 страниц
пагинации. Ожидается ~120 записей.

Сбор товаров со scrapingcourse.com (SPA):

    python run_spider.py --spider ecommerce --output products.json

Использует Playwright для JS-рендеринга. Обходит 10 страниц пагинации.
Ожидается ~160 записей.

NewsSpider (SSR):
- Сайт: habr.com/ru/articles
- Технология: обычный Scrapy (scrapy.Request)
- Пагинация: 6 страниц × 20 статей = 120 записей
- Данные: title, url, date, summary, source, hub
- Особенности: фильтрация по дате (--days) и ключевым словам (--keywords)

EcommerceSpider (SPA):
- Сайт: scrapingcourse.com/ecommerce
- Технология: Scrapy + Playwright (JS-рендеринг)
- Пагинация: 10 страниц × 16 товаров = 160 записей
- Данные: title, price, rating, url, description
- Особенности: ожидание селектора li.product через PageMethod

-----------------------------------------------------------
PIPELINES
-----------------------------------------------------------

1. CleaningPipeline
   - Исправляет битые кодировки через ftfy.fix_text()
   - Нормализует пробелы: ' '.join(text.split())
   - Не приводит к нижнему регистру — оригинальный регистр
     сохраняется для дальнейшего NLP-анализа (NER, sentiment)

2. DuplicationPipeline
   - Хранит set() посещенных URL
   - Дропает дубликаты через DropItem
   - Критично для e-commerce: один товар может встречаться
     на нескольких страницах

3. ValidationPipeline
   - Проверяет обязательные поля: title, url
   - Дропает записи с пустыми значениями
   - Гарантирует, что в результат не попадут «мусорные» items

-----------------------------------------------------------
АВТОПРОВЕРКА ТРЕБОВАНИЙ
-----------------------------------------------------------

Оба паука переопределяют метод closed(), который автоматически
проверяет количество собранных items:

- ≥ 100  →  INFO: OK: собрано N items (требуется 100+)
- < 100  →  WARNING: !!! ВНИМАНИЕ: собрано только N items

Это гарантирует, что требование «минимум 100 записей» проверяется
на каждом запуске, а не «на глаз».

ОТСТУПЛЕНИЯ ОТ БУКВЫ ЗАДАНИЯ И ИХ ОБОСНОВАНИЕ
-----------------------------------------------------------

1. ECOMMERCE ПАРСИТ SCRAPINGCOURSE.COM, А НЕ WILDBERRIES/OZON

Что было в задании: примеры магазинов — Wildberries, Ozon, Яндекс.Маркет.

Что сделано: использован тренировочный SPA scrapingcourse.com
(160 товаров, полноценная пагинация, динамическая загрузка).

Почему не WB/Ozon:

Wildberries и Ozon используют промышленные антибот-системы:
- Wildberries — собственная защита (HTTP 498 «Bot detected»),
  блокировка по TLS-fingerprint и IP-адресу
- Ozon — Cloudflare + DataDome (анализ поведения, отпечаток браузера)

Что требуется для реального обхода:
1. Резидентные прокси (домашние IP-адреса)
2. Stealth-библиотеки — playwright-stealth, undetected-chromedriver,
   подмена TLS-fingerprint через curl_cffi
3. Anti-Captcha-сервис
4. Распределенный сбор — несколько инстансов с ротацией IP


Попытки запуска EcommerceSpider на Wildberries в рамках этой работы
приводили к блокировке (HTTP 498 на первом же запросе с дата-центрового IP),
что подтверждает вывод.

Механика парсинга на scrapingcourse.com полностью аналогична той,
что нужна для WB/Ozon — отличается только наличие прокси и обход капчи.

2. --CATEGORY И --STORES НЕ ВЛИЯЮТ НА ВЫБОРКУ

Что есть в CLI: аргументы принимаются и логируются.

Что не работает: на scrapingcourse.com они не влияют на выборку — сайт
не поддерживает параметризованный поиск по категориям.

Зачем оставлены: при переходе на реальный магазин (например, WB)
достаточно поменять start_urls в ecommerce.py:

    start_urls = [f'https://search.wb.ru/exactmatch/ru/common/v4/search?query={self.category}']

CLI-интерфейс при этом не меняется — параметры уже есть.

3. LOWER В CLEANINGPIPELINE НЕ ПРИМЕНЯЕТСЯ

Что было в лекции: «# lower если нужно» — то есть опционально.

Что сделано: сознательно убран. Приведение к нижнему регистру ломает:
- NER — «Apple» и «apple» — разные сущности
- Sentiment Analysis — «Отлично!» и «отлично!» различаются
- Классификацию — теряется информация о регистре

Для BoW/TF-IDF lower можно включить одной строкой в pipelines.py.

4. ANTI-CAPTCHA НЕ РЕАЛИЗОВАНО

Причина: требует платный API-ключ (2captcha.com, anti-captcha.com).

Кроме того:
«Юридические риски: многие сайты запрещают автоматизированный сбор
в ToS, обход капчи может нарушать законодательство».

5. REDIS НЕ РЕАЛИЗОВАНО

Причина: Redis нужен для распределенной очереди URL при параллельном
запуске нескольких инстансов Scrapy (масштабирование). Для одного паука
на локальной машине избыточен.

-----------------------------------------------------------
ОГРАНИЧЕНИЯ
-----------------------------------------------------------

- --category/--stores — резерв для реальных магазинов, на учебном
  сайте не работают
- Playwright в settings глобально — News Spider тоже запускает
  Chromium (небольшой overhead, но не критично)
- MAX_PAGES зашит в код — для сбора большего количества нужно
  править константу в пауке
- Обход роботс-файлов — для scrapingcourse.com отключен ROBOTSTXT_OBEY
  в custom_settings (тренировочный сайт); для Хабра robots.txt соблюдается
- Anti-Captcha и Redis — не реализованы по причинам выше
