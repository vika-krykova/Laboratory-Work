# Практика 9: End-to-End пайплайн рекомендательной системы

Этот проект представляет собой сквозной (end-to-end) пайплайн обработки данных и машинного обучения, упакованный в Docker Compose и оркестрируемый с помощью Apache Airflow. 
В качестве бизнес-логики используется рекомендательная система (SVD, ALS, Content-based), разработанная в рамках Практики 7-8. Пайплайн симулирует ежедневный сбор данных, их валидацию, обучение моделей и загрузку метрик в базу данных.

## Как работает пайплайн (DAG)

DAG recsys_daily_pipeline запускается по расписанию (каждый день в 3:00) и состоит из 4 задач с жесткими зависимостями:

    collect_data — симуляция сбора данных (в реальном проекте здесь был бы парсинг или выгрузка из API).

    validate_and_quarantine — проверка схемы данных через pandera. Если типы данных или диапазоны не совпадают (например, рейтинг > 5.0), битые строки отправляются в /tmp/quarantine, а пайплайн продолжает работу с чистыми данными.

    train_models — запуск recsys.py через BashOperator. Обучаются модели, считаются метрики (Precision, Recall, NDCG).

    load_to_db — идемпотентная загрузка результатов в PostgreSQL.

## Надежность и идемпотентность
1. Идемпотентность (UPSERT): В pipeline/load.py реализована SQL-конструкция ON CONFLICT DO UPDATE. Это значит, что сколько бы раз вы ни запустили пайплайн, количество строк в базе не увеличится (не будет дубликатов), а данные просто перезапишутся актуальными значениями.
2. Ретраи: В DAG настроено свойство retries=3. Если задача упадет из-за временного сбоя сети, Airflow попробует выполнить ее еще 2 раза.
3. Карантин: Некорректные данные не "роняют" весь пайплайн, а изолируются и сохраняются в отдельную папку для дальнейшего анализа аналитиком.

## Описание скриншотов (папка `docs/`)

В папке `docs` собраны доказательства работы пайплайна и результаты проверки сбоями:

*   **`1_success.jpg`** — Демонстрация успешного прогона DAG. Все 4 задачи выполнены без ошибок (зеленый граф).
*   **`2_validation_error.jpg`** — Тест на битые данные. Имитация подмены типа (строка вместо числа) привела к падению задачи `validate_and_quarantine`.
*   **`3_network_fail.jpg`** — Тест на отключение сети. Имитация недоступности БД (неверный хост) переводит задачу `load_to_db` в статус `up_for_retry` (ожидание повтора).
*   **`3_retries.jpg`** — Тест на таймаут. Установка `execution_timeout=1s` привела к принудительной остановке задачи и 3 повторным попыткам (Retries).
*   **`4_db_before_after.jpg`** — Проверка идемпотентности. Два скриншота терминала в одном: до и после повторного запуска пайплайна. Количество строк в БД не изменилось (108 строк).
*   **`5_empty_data.jpg`** — Тест с пустым файлом. Подача датафрейма с 0 строк приводит к ожидаемому падению пайплайна (защита от "успешной" обработки пустоты).

## Ограничения (Limitations)
В рамках учебного проекта были сознательно допущены следующие упрощения:
1. Синтетические данные: На этапе collect_data генерируются синтетические данные (10 пользователей, 20 фильмов), чтобы продемонстрировать работоспособность пайплайна без скачивания тяжелых датасетов. В реальном проекте здесь был бы реальный источник (S3, API, FTP).
2. Алерты: Интеграция с Telegram-ботом или email-уведомлениями не настроена, так как требует внешних API-токенов. Мониторинг сбоев осуществляется через веб-интерфейс Airflow.
3. Масштабирование: Используется LocalExecutor в Airflow. Для больших объемов данных потребовался бы CeleryExecutor с Redis и отдельными воркерами.
